# 서비스 기획 명세 (문제 한 줄 → 문서 → 코드)

모든 산출물은 현재 레포의 `docs/spec/`에 마크다운으로 둔다. 문서끼리, 그리고 문서와 코드는 **ID**로만 연결한다.
ID는 한 번 붙이면 바꾸거나 다시 쓰지 않는다(지운 항목은 `~~취소선~~`과 `(폐기: 날짜)`로 남긴다).

| 접두어 | 뜻 | 파일 |
|---|---|---|
| `GOAL-` | 목표·성공 지표 | `00-overview.md` |
| `REQ-` | 요구사항 | `01-requirements.md` |
| `FN-` | 기능 | `02-features.md` |
| `FLOW-` | 유저플로우 | `03-userflow.md` |
| `POL-` | 정책(규칙·수치·예외) | `04-policy.md` |
| `SCR-` | 화면 | `05-screens.md` |
| `TBL-` | DB 테이블 | `06-db.md` |
| `QA-` | 검사 항목 | `07-qa.md` |
| — | 변경이력 | `CHANGELOG.md` |

인자를 보고 모드를 고른다. `docs/spec/`이 없을 때: 레포에 앱 코드가 이미 있거나 "기존 코드에서" 라고 하면 **0. 기존 코드에서 만들기**,
아니면 **1. 새로 만들기**. `docs/spec/`이 있으면 요청 문장으로 판단한다
("구현·만들어·개발" → 구현, "고쳐·바꿔·추가" → 수정, "확인·점검·맞는지" → 점검). 애매하면 한 번 묻는다.

## 0. 기존 코드에서 만들기 (역기획)

이미 있는 프로젝트의 코드를 읽고 지금 상태 그대로를 명세로 옮긴다. 이 단계에서는 동작을 바꾸지 않는다.

1. **훑기**: 코드가 많으니 메인이 직접 읽지 않는다. `Explore` 에이전트에 아래 목록을 `파일:줄`과 함께 뽑아 달라고 맡긴다.
   - 라우트·페이지·화면 컴포넌트(→ `SCR-`), 사용자가 할 수 있는 동작·API 엔드포인트(→ `FN-`)
   - 코드에 박힌 숫자·기간·권한·계산식·예외 처리(→ `POL-`), 스키마·마이그레이션·모델(→ `TBL-`)
   - 기존 테스트(→ `QA-`), README·주석·커밋 메시지에 적힌 목적(→ 개요·`REQ-` 근거)
2. **작성**: 그 목록을 `model: "sonnet"` 에이전트에 넘겨 1번 새로 만들기와 **같은 형식**으로 문서를 쓰게 한다. 다른 점은 이것뿐이다.
   - 항목마다 `근거: 파일:줄`을 붙인다. 코드에 없는 기능·정책은 쓰지 않는다.
   - 코드로 알 수 없는 것(왜 이 숫자인지, 목표 지표, 대상 사용자)은 지어내지 않고 `확인 필요:` 로 적는다.
   - 계산·돈·권한이 걸린 `POL-`은 식을 코드 그대로 옮기고 단위(원·%·일)를 적는다.
   - 기존 테스트가 있는 `QA-`는 상태 `통과`(돌려서 확인한 경우만)와 위치를, 없으면 `미확인`.
3. **연결 표시**: 근거 위치의 함수·컴포넌트·마이그레이션 위에 `spec: FN-…` 주석 한 줄만 단다. 다른 코드는 건드리지 않는다.
   파일이 많으면 하이쿠 `haiku-helper`에 `ID → 파일:줄` 표를 넘겨 기계적으로 달게 한다.
4. **되묻기**: `확인 필요` 항목을 모아 `AskUserQuestion`으로 묻는다(한 번에 최대 4개, 중요한 것부터). 답을 문서에 반영하고 나머지는 목록으로 남긴다.
5. **점검**(4번)을 돌리고, 코드와 명세가 어긋나 보이는 곳(버그로 의심되는 것 포함)은 고치지 말고 보고서에 "의심" 표로 올린다.
6. `CHANGELOG.md`에 `## 날짜 v1 기존 코드에서 작성 (커밋 <해시>)`. 이후는 수정·구현·점검 모드를 그대로 쓴다.

## 1. 새로 만들기

1. **되묻기(한 번만)**: 문제 한 줄로 정할 수 없는 것만 `AskUserQuestion`으로 묻는다(최대 3개).
   보통 ① 누가 쓰나(사용자 유형) ② 어디서 쓰나(웹·앱·사내 도구) ③ 지금 수치가 있나(성공 지표의 출발점).
   답이 없으면 그럴듯한 가정을 세우고 `00-overview.md`의 "가정" 절에 적는다.
2. **문서 작성 순서**: 개요 → 요구사항 → 기능 → 정책 → 유저플로우 → 화면 → DB → QA. 앞 문서의 ID를 뒤 문서가 참조한다.
3. 각 문서의 형식:
   - `00-overview.md`: 문제(사용자 문장 그대로 인용), 대상 사용자, `GOAL-` 표(지표·현재·목표·측정 방법, 예: 노쇼율 31%→10%),
     범위 안/밖, 가정.
   - `01-requirements.md`: `| ID | 요구사항 | 근거(GOAL) | 우선순위(필수/권장/나중) |`. 한 줄에 하나, "~할 수 있어야 한다" 꼴.
   - `02-features.md`: 기능마다 `### FN-001 이름` + `충족: REQ-…` + 설명 + **수용 기준**(Given/When/Then 2~4개) + `관련: POL-…, SCR-…, TBL-…`.
   - `04-policy.md`: 규칙마다 `### POL-001` + 한 문장 규칙 + 수치·시간·권한을 숫자로 + 예외 + `적용: FN-…`.
     예: "시작 10분 뒤에도 체크인이 없으면 예약을 자동 취소한다."
   - `03-userflow.md`: 흐름마다 `### FLOW-001` + mermaid `flowchart` + 단계별 관련 `SCR-`/`FN-`. 실패·예외 분기도 그린다.
   - `05-screens.md`: 화면마다 `### SCR-001` + 목적 + 텍스트 와이어프레임(코드 블록) + 요소 표(요소·동작·`FN-`) + 빈 상태·오류 상태.
   - `06-db.md`: mermaid `erDiagram` 하나 + 테이블마다 `### TBL-001 이름`과 칼럼 표(이름·타입·제약·설명) + 그대로 쓸 수 있는 DDL.
     DDL 방언은 레포에 이미 쓰는 DB를 따르고, 없으면 PostgreSQL.
   - `07-qa.md`: `| ID | 대상(FN/POL) | 확인 방법 | 기대 결과 | 상태(미확인/통과/실패) | 테스트 위치 |`.
     모든 `FN-` 수용 기준과 수치가 있는 모든 `POL-`이 QA 항목을 하나 이상 가진다.
   - `CHANGELOG.md`: `## YYYY-MM-DD v1 최초 작성` + 만든 ID 범위.
4. 작성은 문서가 많으니 `model: "sonnet"` 에이전트 하나에 위 형식과 1번 답을 넘겨 맡기고, 메인은 아래 **점검**을 돌려 결과를 확인한다.
5. 보고: 목표 지표, 기능 수, 정책 수, 화면 수, 테이블 수, 가정 목록, 그리고 "다음에 할 일"(구현 시작 `FN-` 추천 순서).

## 2. 수정 (제안 → 승인 → 반영)

1. 요청과 관련된 ID를 `grep -rn "ID" docs/spec/`으로 찾아 **영향받는 모든 문서**를 고른다(정책 하나가 기능·화면·DB·QA·코드에 걸친다).
2. 바로 고치지 않는다. 제안을 번호로 보여 준다: `제안 n: [파일] ID — 지금 → 바뀜 (이유)`. 코드에 `spec:` 표시가 있는 ID면 "코드도 바뀜"을 붙인다.
3. `AskUserQuestion`(multiSelect)으로 반영할 제안을 고르게 한다. 고른 것만 고친다.
4. 반영 후 `CHANGELOG.md`에 `## 날짜 vN 한 줄 요약` + 바뀐 ID + 승인된 제안 번호, 거절된 제안은 "보류"로 적는다.
5. 바뀐 `FN-`/`POL-`의 QA 상태는 `미확인`으로 되돌리고, 코드가 있으면 3번 구현 모드의 해당 ID 작업으로 이어 간다.

## 3. 구현 (명세 → 코드)

1. 대상: 사용자가 ID를 주면 그것만, 아니면 우선순위 `필수` 기능부터 하나씩. 시작 전에 고를 `FN-` 목록과 순서를 보여 준다.
2. 기능 하나마다: 그 `FN-`의 수용 기준, 연결된 `POL-`·`SCR-`·`TBL-`만 읽는다(문서 전체를 다시 읽지 않는다).
3. 레포의 기존 구조·프레임워크를 따른다. 레포가 비었으면 스택을 한 번 묻는다.
4. **연결 표시**: 그 기능·정책을 구현한 함수·컴포넌트·마이그레이션 바로 위에 주석 한 줄 `spec: FN-003, POL-002`.
   테스트에도 `spec: QA-005`를 붙인다. 주석은 이것만 넣는다.
5. 수치 정책(`10분` 같은)은 코드에 흩지 않고 상수 하나로 두고 그 위에 `spec: POL-…`.
6. 수용 기준마다 테스트를 하나 쓰고 돌린다. 통과하면 `07-qa.md`의 상태를 `통과`, 테스트 위치를 `파일:줄`로 채운다.
7. 구현 중 명세가 틀렸거나 비었음을 알면 코드로 몰래 정하지 않는다. 2번 수정 모드의 제안으로 올린다.
8. 여러 기능을 한꺼번에 하면 전역 규칙 "모델 사다리"대로 나눈다(평범한 화면·CRUD는 sonnet, 계산·상태 전이·권한은 opus, 돈·인증은 fable-expert 검토).

## 4. 점검 (명세 ↔ 코드)

새로 만든 뒤, 수정한 뒤, 구현한 뒤, 그리고 사용자가 요청할 때 돌린다.

```bash
cd docs/spec
# 정의된 ID(### 제목이나 표 첫 칸)와 참조된 ID
grep -ohE '^(### |\| )(GOAL|REQ|FN|FLOW|POL|SCR|TBL|QA)-[0-9]+' *.md | grep -oE '[A-Z]+-[0-9]+' | sort -u > /tmp/spec-defined
grep -ohE '\b(GOAL|REQ|FN|FLOW|POL|SCR|TBL|QA)-[0-9]+' *.md | sort -u > /tmp/spec-used
comm -13 /tmp/spec-defined /tmp/spec-used    # 정의 없이 참조만 된 ID
cd - >/dev/null
# 코드가 가리키는 ID
grep -rhoE 'spec: [A-Z]+-[0-9]+(, [A-Z]+-[0-9]+)*' --exclude-dir={node_modules,.git,dist,build,docs} . | grep -oE '[A-Z]+-[0-9]+' | sort -u > /tmp/spec-code
comm -13 /tmp/spec-defined /tmp/spec-code    # 코드에 있는데 명세에 없는 ID
comm -23 <(grep -E '^(FN|POL)-' /tmp/spec-defined) /tmp/spec-code   # 아직 구현 안 된 기능·정책
```

이 밖에 눈으로 확인할 것: `REQ-`마다 충족하는 `FN-`이 있나, `FN-`마다 `QA-`가 있나, 폐기된 ID를 아직 참조하는 곳이 있나.
결과는 `| 문제 | ID | 위치 | 고칠 방법 |` 표로 보고하고, 고치는 것은 2번 수정 모드로 넘긴다.
